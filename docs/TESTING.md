# Тестирование

Три уровня: от быстрого, без аккаунтов, до сквозной проверки в настоящем OkoCRM.

| Уровень | Что проверяет | Нужно |
|---|---|---|
| 1. Автотесты | Логику моста: подписи, идемпотентность, статусы, ошибки, повторы | Только Python |
| 2. Симулятор OkoCRM | Настоящую авторизацию, баланс и отправку в REDSMS | Аккаунт REDSMS |
| 3. Личный виджет | Весь путь через интерфейс OkoCRM | REDSMS, OkoCRM, публичный HTTPS |

## 1. Автотесты

```bash
python3 -W ignore -m unittest discover -s tests -v
```

[tests/test_bridge.py](../tests/test_bridge.py) поднимает фейковые REDSMS и OkoCRM на localhost и проверяет:

- запрос с неверной подписью получает 403;
- `installed` → `PUT senders` + `POST status ok`, подпись REDSMS `md5(ts + key)`;
- неверный ключ REDSMS → `POST status error`;
- `sms.send` → `POST /api/message` с `dlrUrl`, потом события `sent` и `delivered`;
- повтор с тем же `message_key` возвращает тот же `message_id` без второй SMS;
- отказ REDSMS (400) и статусы-ошибки (`stop_list` и др.) → `failed` с причиной;
- колбэк с поддельной подписью в URL игнорируется;
- отложенная отправка передаёт `startTime`, а дальше 7 дней отклоняется;
- неизвестное или удалённое подключение получает 409;
- потерянный колбэк восстанавливается опросом REDSMS;
- неподходящие имена отправителей перечислены в тексте ошибки;
- номер вроде «123» отклоняется сразу, без запроса в REDSMS;
- одновременные колбэк и опрос дают ровно одно событие статуса, `failed` после `delivered` не отправляется;
- старые сообщения удаляются, `/healthz` проверяет базу, миграция старой схемы БД работает.

Тесты автоматически запускаются в GitHub Actions на Python 3.9 и 3.12 при каждом push ([.github/workflows/tests.yml](../.github/workflows/tests.yml)).

Тесты обязательны перед каждым коммитом. Новое поведение — новый тест в том же файле.

## 2. Симулятор OkoCRM + настоящий REDSMS

[tools/simulate.py](../tools/simulate.py) изображает OkoCRM. Он шлёт в мост подписанные `installed` и `sms.send` и печатает всё, что мост отправляет «в OkoCRM».

Терминал 1, мост:

```bash
OKOCRM_API_BASE=http://127.0.0.1:9900/v4/sms OKOCRM_WIDGET_PRIVATE_KEY=test APP_SECRET=test \
PUBLIC_BASE_URL=https://example.com POLL_AFTER_MINUTES=1 DB_PATH=/tmp/okocrm-redsms-test.sqlite3 \
python3 -m okocrm_redsms
```

Терминал 2, только проверка ключа и баланса, без SMS:

```bash
python3 tools/simulate.py --login ЛОГИН --api-key КЛЮЧ --sender ИМЯ
```

Ожидается `PUT /v4/sms/senders`, затем `POST /v4/sms/status {"status": "ok"}`. Если пришёл `error`, причина будет в `message`.

Отправка настоящей SMS (платно):

```bash
python3 tools/simulate.py --login ЛОГИН --api-key КЛЮЧ --sender ИМЯ --phone +7XXXXXXXXXX
```

Ожидается ответ `{"message_id": "rs-…"}`, затем событие `sent`, а через 1–2 минуты `delivered`. Колбэк REDSMS до локальной машины не дойдёт, поэтому статус приходит опросом REDSMS.

## 3. Сквозная проверка в OkoCRM

Нужен публичный HTTPS. Это либо боевой сервер из [CONNECT.md](CONNECT.md), либо временный туннель:

```bash
cloudflared tunnel --url http://localhost:8080
```

Адрес туннеля нужно прописать в `widget/config.json` и `PUBLIC_BASE_URL`. Через туннель проверка IP колбэков REDSMS не пройдёт, поэтому на время теста задайте `REDSMS_ALLOWED_IPS=` (пусто).

Чеклист на личном виджете (основан на чеклисте из документации OkoCRM):

- [ ] Сохранение настроек → в логах `installed`, во вкладке «Подключение» видны имена отправителей
- [ ] SMS из карточки контакта → в ленте сообщение с одной галкой, ответ укладывается в 4 с
- [ ] После доставки — две галки
- [ ] SMS на заведомо неверный номер → красная заметка с причиной, «Повторить» отправляет заново
- [ ] Отложенная отправка (шаблон/автодействие с `send_at`) уходит в указанное время
- [ ] Автодействие «Отправить SMS» в воронке работает, отправитель подставляется
- [ ] Неверный ключ API в настройках → кнопка SMS гаснет, виден текст ошибки; после исправления — снова работает
- [ ] Изменение имён отправителей → новый список во вкладке «Подключение»
- [ ] «Перевыпустить» токен → новый `installed`, отправка продолжает работать
- [ ] Удаление виджета → `uninstalled` в логах

Только после этого можно публиковать виджет как публичный.
