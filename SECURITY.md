# Безопасность

## Как сообщить об уязвимости

Не публикуйте её в открытых Issues. Напишите на [email безопасности] или создайте приватный отчёт: GitHub → Security → Report a vulnerability. Ответим в течение [3 рабочих дней].

## Что защищаем

| Данные | Где | Почему важно |
|---|---|---|
| Ключи API REDSMS клиентов | БД моста | С ключом можно отправлять SMS за счёт клиента |
| Токены подключений OkoCRM | БД моста | С токеном можно писать в ленту CRM клиента |
| Номера телефонов получателей | БД, логи | Персональные данные (152-ФЗ) |
| Тексты SMS, в том числе коды подтверждения | БД, пока сообщение в очереди | С кодом можно войти в чужой аккаунт |
| Секретный ключ виджета, `APP_SECRET`, `ENCRYPTION_KEY` | Переменные окружения или файлы | Позволяют подделывать запросы и расшифровать БД |

## Меры защиты

### Входящие запросы
- **Подпись OkoCRM.** HMAC-SHA256 по сырому телу запроса ключом виджета, сравнение за постоянное время. Запросы без верной подписи получают 403.
- **Защита от повтора.** Поле `time` входит в подписанное тело. Запрос старше `SIGNATURE_MAX_AGE` (по умолчанию 15 минут) отклоняется, поэтому перехваченный `uninstalled` или `sms.send` позже не переиграть. Повтор в пределах окна безопасен: `sms.send` идемпотентен по `message_key`.
- **Колбэки REDSMS.** Свою подпись REDSMS не присылает, поэтому:
  - адрес `dlrUrl` содержит 128-битный HMAC от `setting_ulid` на `APP_SECRET`, без него — 404;
  - запросы принимаются только с IP REDSMS;
  - статус применяется, только если `uuid` принадлежит сообщению этого подключения.
- **Устойчивость HTTP-сервера:**
  - тело запроса не больше 1 МБ;
  - таймаут сокета 20 с, медленные клиенты не держат потоки;
  - не больше `MAX_CONCURRENT_REQUESTS` одновременных запросов, сверх лимита сразу 503;
  - некорректный `Content-Length` получает 400;
  - версия Python в заголовках не раскрывается.

### Хранение
- **Шифрование секретов и персональных данных.** Ключи API, токены и номера телефонов зашифрованы Fernet (AES-128-CBC + HMAC-SHA256) ключом `ENCRYPTION_KEY`.
- **Коды подтверждения не хранятся.** Текст SMS стирается сразу после передачи в REDSMS.
- **Поиск без расшифровки.** Лимиты по номеру и тексту считаются по HMAC-индексам (blind index), для них выделен отдельный подключ.
- **Сроки хранения.** Завершённые сообщения удаляются через `RETENTION_DAYS` (30 дней). При удалении виджета токен и ключ API стираются сразу.
- **Защита ключа шифрования.** С чужим ключом сервис не стартует, данные не портятся. Ключ меняется без простоя (`ENCRYPTION_KEY=новый,старый`).

### Логи
- **Номера маскируются** (`+7999***4567`), в том числе внутри текстов ошибок REDSMS.
- **Секреты в лог не попадают:** ни токены, ни ключи API, ни тексты SMS.

### Исходящие запросы
- **Только HTTPS.** Адреса REDSMS, OkoCRM и `PUBLIC_BASE_URL` обязаны быть `https://`. Исключение — явный `ALLOW_INSECURE_URLS=true` для локальной отладки.
- **Редиректы не выполняются**, поэтому ключ API не уйдёт на чужой адрес.

### Злоупотребления
- **Лимиты отправки:** в минуту и в час на подключение, в час на номер, запрет дублей. Защищают деньги клиента от зацикленных автодействий.

### Конфигурация и инфраструктура
- **`APP_SECRET`** не короче 32 символов, иначе сервис не стартует.
- **Секреты из файлов** (`*_FILE`, Docker secrets): их не видно в `docker inspect` и в окружении процессов.
- **Ограниченный контейнер:**
  - запуск не от root (uid 10001);
  - `--read-only`, `--cap-drop ALL`, `no-new-privileges`;
  - порт опубликован только на `127.0.0.1`, наружу — через TLS-прокси.

### Цепочка поставки
- **Одна зависимость** — `cryptography`. Остальное из стандартной библиотеки Python.
- **CI с минимальными правами:** `contents: read`, без сохранения учётных данных git.
- **Автоматические проверки в CI:**
  - `pip-audit` — известные уязвимости в зависимостях;
  - `bandit` — статический анализ кода.
- **Dependabot** еженедельно предлагает обновления pip-зависимостей и Docker-образа, раз в месяц — GitHub Actions.

## Известные ограничения

| Ограничение | Почему | Что снижает риск |
|---|---|---|
| Авторизация REDSMS — `md5(ts + ключ)` | Так устроен протокол REDSMS | Ключ не передаётся, `ts` уникален на каждый запрос, всё идёт по HTTPS |
| REDSMS не подписывает колбэки | Протокол REDSMS | HMAC в URL, белый список IP, привязка `uuid` к подключению |
| Ключ шифрования лежит на том же сервере, что и БД | Нет внешнего KMS | Храните ключ отдельно от резервных копий БД, используйте `*_FILE` и шифрование диска |
| Тексты сообщений в очереди (секунды) и с отложенной отправкой (до 7 дней) хранятся зашифрованными | Нужны для отправки | Стираются сразу после передачи в REDSMS |
| Защита от повтора опирается на часы сервера | Подпись OkoCRM не содержит отдельной метки времени | Синхронизируйте время (NTP). Окно меняется через `SIGNATURE_MAX_AGE` |

## Чек-лист оператора

- [ ] `ENCRYPTION_KEY`, `APP_SECRET` и ключ виджета сгенерированы случайно и хранятся в менеджере паролей
- [ ] Секреты переданы файлами (`*_FILE`), а не через `.env` в репозитории
- [ ] Контейнер запущен с флагами из [docs/CONNECT.md](docs/CONNECT.md), порт только на `127.0.0.1`
- [ ] TLS на прокси, `TRUST_X_FORWARDED_FOR=true` только за своим прокси
- [ ] Резервные копии БД хранятся отдельно от `ENCRYPTION_KEY`
- [ ] На сервере включена синхронизация времени (NTP)
- [ ] Предложения Dependabot смотрятся и вливаются
- [ ] Доступ к серверу и логам — только у тех, кому он нужен
